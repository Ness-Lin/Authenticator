- 更新日期：2026-09-07
- 适用版本：Android 首版（MVP）
- 文档目录：项目根目录 `docs/`，所有后续设计、API、开发及测试文档必须存放于此目录或其子目录

## 1. 背景与目标

开发使用 Kotlin 编写的离线双因素认证应用，提供与 Google Authenticator、Microsoft Authenticator 中标准动态验证码功能相近的体验。用户可以扫描二维码或手动输入共享密钥，在本机生成验证码，并安全导出账户配置。

本应用保存的是生成验证码所需的账户和密钥，不是仅保存某一时刻的验证码。添加成功表示本机配置已保存，不代表服务端绑定已完成；用户仍需到原服务输入验证码完成验证。

目标包括：

1. 无网络环境下正常生成、展示和更新 TOTP 验证码。
2. 采用 api-impl-ui 模块隔离，为后续 Kotlin Multiplatform（KMP）迁移预留接口与平台适配边界。
3. 敏感信息加密存储，默认加密导出，不上传共享密钥。
4. 使用 Material 3 与 Jetpack Compose 构建清晰、可访问的 Android 界面。

## 2. 现状与范围

当前工程为 `:app` 单模块 Compose 模板，尚未实现认证账户、扫描、生成、存储或导出业务。本轮交付仅包括本文与开发规范，不包含代码变更。

### 2.1 首版范围

| 编号 | 能力 | 优先级 |
| --- | --- | --- |
| FR-01 | 扫描标准 otpauth TOTP 二维码并确认添加 | 必须 |
| FR-02 | 手动输入密钥及参数添加账户 | 必须 |
| FR-03 | 验证码列表、倒计时、自动更新、复制 | 必须 |
| FR-04 | 账户搜索、名称编辑、删除及重复提示 | 必须 |
| FR-05 | 选择账户、安全导出与显式明文兼容导出 | 必须 |
| FR-06 | 本地加密存储、应用锁及敏感操作认证 | 必须 |
| FR-07 | 空状态、错误反馈、权限处理、无障碍和深浅色主题 | 必须 |

### 2.2 首版不包含

- HOTP 计数器验证码、Steam 等非标准验证码。
- Microsoft 等厂商的推送批准、免密登录、设备注册、企业身份协议。
- Google Authenticator 的 `otpauth-migration://` 私有批量迁移协议。
- 云同步、账户登录、服务端、在线密钥托管、广告与统计 SDK。
- 加密备份文件的应用内恢复、图库识别二维码、二维码图片导出。
- iOS 或桌面客户端；本期仅设计可迁移边界，不承诺直接复用整个 Android UI。

加密备份恢复是后续优先能力。首版导出页面必须明确说明当前版本不支持文件恢复，不得宣传已经具备完整备份恢复闭环；格式正确性必须通过独立解密测试验证。

## 3. 用户流程

### 3.1 首次启动

展示空列表及扫描、手动添加入口；说明数据仅保存在本机，卸载或丢失设备可能导致无法使用验证码，需保留原服务恢复码。首次不申请相机权限。应用锁默认启用，依赖系统安全锁屏；未设置时引导设置，拒绝设置则不能进入密钥保存流程。

### 3.2 扫描添加（FR-01）

1. 用户主动进入扫描页时申请相机权限。
2. 在本机识别二维码，不上传画面或识别内容。
3. 验证协议及参数，进入账户确认页，不直接写入数据库。
4. 展示发行方、账户名、算法、位数与周期，密钥默认掩码显示。
5. 用户确认后原子保存并返回列表。

要求：

- 使用背面相机，支持设备具备的手电筒开关；暂停、后台或离开页面立即释放相机。
- 拒绝权限时允许改用手动添加；永久拒绝时提供系统设置入口。
- 同一次扫描只导航一次；重复帧不得创建重复账户。
- 非认证二维码、参数非法、HOTP、私有迁移码分别提示可理解的原因。
- URI 解析失败不得自动跳转浏览器或执行二维码内容。
- 相机不可用、识别失败和取消操作不得产生半成品记录。

### 3.3 手动添加（FR-02）

| 字段 | 规则 |
| --- | --- |
| 发行方 | 可选，去除两端空白，最多 128 个 Unicode 码点 |
| 账户名 | 必填，去除两端空白，最多 256 个 Unicode 码点 |
| 密钥 | 必填，Base32；忽略用户输入的空格和连字符，大小写不敏感；保存为规范化后的密钥字节 |
| 类型 | 首版仅 TOTP |
| 算法 | 默认 SHA-1，支持 SHA-256、SHA-512 |
| 位数 | 默认 6，支持 8 |
| 周期 | 默认 30 秒，支持整数 15–120 秒 |

算法、位数和周期置于高级选项。密钥输入默认隐藏，可显式切换可见性；禁用自动填充、自动纠错及个性化学习。禁止回显完整密钥到错误信息。校验通过前不能提交；保存失败保留当前前台表单供重试，但不把密钥写入可持久化界面状态。

解码后的密钥支持 10–128 字节。低于 16 字节给出兼容性安全警告并要求确认；超出范围拒绝。此限制属于本产品支持范围，不声称覆盖所有历史服务配置。

### 3.4 列表与验证码（FR-03、FR-04）

- 展示发行方、账户名、验证码、剩余有效秒数；没有发行方时以账户名为主要标题。
- 验证码视觉上分组但复制结果只有数字，保留前导零。
- 按创建顺序稳定展示，支持按发行方和账户名本地搜索。
- 可修改账户名和发行方；首版不直接修改既有密钥或算法，需要删除后重新添加。
- 删除前确认并说明不会解除原服务的两步验证；失败时记录保持可用。
- 相同密钥、算法、位数和周期视为相同凭据，即使名称不同也提示重复，默认不重复保存；允许用户再次明确确认保留副本。
- 复制后给予反馈；剪贴板标记为敏感，约 30 秒后在仍持有该条目时尽力清除，不覆盖用户后来复制的内容。说明系统或其他应用可能读取剪贴板，清除不构成绝对保密保证。
- 空列表、无搜索结果、加载失败、已锁定、密钥不可用分别展示对应状态，不展示模拟验证码。

### 3.5 导出（FR-05）

导出流程为：选择一个或多个账户 → 选择格式 → 阅读安全说明 → 系统重新认证 → 设置加密口令（加密格式）→ 系统文件选择器选择目的地 → 写入并报告结果。

- 默认格式为加密备份；明文兼容格式需要单独的风险确认，不能记忆为默认选择。
- 重新认证每次导出都必须执行，不使用长时间有效的解锁结果代替。
- 导出为配置快照，包含密钥与生成参数，不导出瞬时验证码。
- 使用 Storage Access Framework 创建文件，不申请全部文件或传统外部存储权限。
- 文件提供方可能是云盘，目的地由用户选择，导出前提示这一边界。
- 不主动发起分享，不创建公共目录中的临时明文文件。
- 用户取消、认证失败或写入失败均不得显示成功；关闭流后才报告完成。
- 无法原子提交的文件提供方可能留下残缺文件，应尽力删除并提示检查目标位置；不承诺撤销第三方已同步的数据。

## 4. 协议与算法要求

### 4.1 TOTP

遵循 RFC 6238，以 RFC 4226 的动态截断方法生成验证码：`T = floor((UnixTimeSeconds - T0) / period)`，`T0 = 0`，计数器为 8 字节大端序。支持 SHA-1、SHA-256、SHA-512 及 6/8 位十进制输出。

使用设备 UTC Unix 时间计算；时区和夏令时不影响结果。不维护递减计数器作为真实时间来源，也不在后台持续轮询。前台恢复、系统时间改变和周期边界时重新计算。设备时间不准时提供检查自动日期时间的提示；不声称离线条件下能够自动判断服务端时差。

### 4.2 otpauth 输入

支持形式：`otpauth://totp/{label}?secret={base32}&issuer={issuer}&algorithm=SHA1&digits=6&period=30`。

- label 与参数采用结构化 URI 解析及 UTF-8 百分号编码，不重复解码；参数值中的加号不得错误转换为空格。
- label 使用可选 `发行方:账户名` 形式，以第一个分隔冒号拆分；参数 issuer 与 label 前缀同时存在而不一致时拒绝并说明冲突。
- 缺省 algorithm/digits/period 使用 SHA-1/6/30；secret 不可缺省，账户名不可为空。
- 拒绝重复的已知参数、非法编码、空密钥、非整数周期、不支持的算法或位数。
- Base32 按 RFC 4648 验证，接受规范尾部填充或省略填充，拒绝非法尾位及错误填充。
- 未知可选参数忽略且不执行；已知参数非法时不得静默回退默认值。
- 单条 URI UTF-8 长度上限 8 KiB，先限制输入大小再解析。

### 4.3 加密导出格式 v1

加密算法采用 AES-256-GCM，口令派生采用 PBKDF2-HMAC-SHA256；加密原语必须使用成熟实现，不自行编写。此格式为本应用版本化格式，不是 Google/Microsoft 通用备份格式。

外层文件为 UTF-8 JSON，建议扩展名 `.authbackup`、MIME `application/json`：

| 字段 | v1 定义 |
| --- | --- |
| format | 固定 `authenticator-backup` |
| version | 整数 1 |
| kdf | 对象，name 为 `PBKDF2-HMAC-SHA256`，iterations 为 600000，salt 为 16 字节随机盐的 Base64 |
| cipher | 对象，name 为 `AES-256-GCM`，nonce 为 12 字节随机数的 Base64，tagBits 为 128 |
| ciphertext | 密文与 16 字节认证标签拼接后进行 Base64 编码 |

- Base64 使用 RFC 4648 标准字母表、带填充、无换行。
- AAD 精确为 ASCII 字节 `authenticator-backup:v1`；v1 的算法、迭代次数、长度、版本必须严格校验，不接受任意算法回退。salt/nonce 改动必须导致校验失败。
- 口令为不做 trim、不做 Unicode 规范化的 UTF-8 字节；长度 12–128 个 Unicode 码点，重复输入必须完全相同；鼓励长口令，不保存口令或派生密钥。
- 每次导出重新生成盐及 nonce，派生 32 字节密钥；口令与设备 Keystore 解耦，保证格式未来可跨设备解密。
- 明文负载为 UTF-8 JSON：`schemaVersion`（1）、`exportedAt`（UTC RFC 3339）、`accounts` 数组。
- 每条账户含 `id`（UUID）、`issuer`（可空字符串）、`accountName`、`type`（totp）、`secret`（大写无填充 Base32）、`algorithm`（SHA1/SHA256/SHA512）、`digits`、`period`、`createdAt`（UTC RFC 3339）。这些信息全部处于密文内部。
- 外层不得出现账户名、发行方、密钥或账户数量。不承诺隐藏文件大小侧信道。
- 未来读取器必须拒绝重复 JSON 字段和未知版本，并在执行 KDF 前校验文件大小及参数；v1 文件上限 10 MiB、账户上限 1000。
- 错误口令、密文损坏与认证失败对用户统一报告无法解密；后续任何格式变更必须新增版本，不静默改变 v1。

### 4.4 明文兼容导出

UTF-8 文本文件，每行一个规范 `otpauth://totp/` URI，以 LF 分隔，无 BOM；建议扩展名 `.txt`、MIME `text/plain`。每条 URI 显式输出 secret、algorithm、digits、period，发行方非空时输出 issuer，并正确百分号编码标签与参数。

该模式泄露可长期生成验证码的共享密钥，必须明确警告。单条 URI 采用业界约定格式，但多行文本并非各厂商统一文件导入标准；不得承诺 Google 或 Microsoft 可直接导入整个文件。

## 5. 安全需求（FR-06）

1. 无网络为默认运行方式，不声明 INTERNET 权限，不接入遥测 SDK。二维码识别依赖必须支持离线分发和运行。
2. 使用 Android Keystore 保护不可导出的 AES 密钥；账户名、发行方、共享密钥及生成参数整体加密，数据库只保留必要的不敏感索引。
3. 本地记录采用 AES-GCM，使用安全随机源生成 nonce；同一密钥不得复用 nonce。AAD 绑定记录 ID 和存储 schema 版本，防止跨记录替换。
4. 应用默认要求系统认证解锁；使用 BiometricPrompt 与系统设备凭据，Android 7–10 的兼容方式须经过实现验证。
5. 冷启动、进程重建及进入后台后均锁定；返回前台需要认证。敏感页面切换至系统文件选择器时也不得在后台保留可见账户内容，恢复策略通过明确的导出状态管理实现。
6. 不将长期密钥放入 SavedStateHandle、Bundle、Intent、导航参数、剪贴板、日志、崩溃上报或未加密 SharedPreferences。
7. 对账户页、密钥表单、导出页启用安全窗口，防止常规截图、录屏及最近任务预览泄露。
8. 关闭系统自动备份及设备迁移中的敏感数据复制，兼顾 Android 12 前后规则，并验证目标系统行为。
9. 密钥失效、密文损坏必须提示恢复途径，不静默生成新密钥覆盖已有数据或清空数据库。
10. 不自建密码学算法；尽量缩短明文在内存中的生命周期，可变缓冲区用后清理。不承诺 JVM、输入法、root 或已被攻陷系统上的绝对安全。
11. 应用锁属于界面访问控制，Keystore 属于静态存储保护；没有使用认证绑定密钥时不得宣传为每次解密都有硬件认证。硬件支持因设备而异，不得声称所有设备均使用 StrongBox。

## 6. 界面与非功能要求

### 6.1 界面与可访问性

- Material 3、Compose、系统深浅色、边到边布局及正确的系统栏与输入法 inset。
- 首页直接展示账户列表，提供明确的添加和导出入口，不设置营销首页。
- 触控目标至少 48 dp；正文对比度至少 4.5:1，不仅靠颜色表达剩余时间或错误。
- 支持 TalkBack；倒计时不逐秒触发无障碍播报，验证码朗读需要用户主动聚焦或操作。
- 在 320 dp 宽度、横屏及 200% 字体缩放下不截断关键操作或发生文字重叠。
- 所有面向用户的文案、无障碍标签、错误、通知和数量文本来自资源文件；至少提供完整简体中文及英文资源，不拼接自然语言句子。

### 6.2 性能与可靠性

以下为待实现的验收目标，不是当前实测数据：

| 场景 | 目标 |
| --- | --- |
| 前台验证码更新 | 周期切换后可见账户在 1 秒内更新，无上一周期代码继续可操作的状态 |
| 100 个账户计算 | 单轮生成计算 p95 不超过 100 ms，不含认证与磁盘读取 |
| 列表规模 | 支持 1000 个账户，使用惰性列表，不按每个账户创建独立循环计时任务 |
| 滚动 | 1000 条账户场景，60 Hz 基准设备超出帧预算的比例低于 5% |
| 冷启动 | 系统认证完成后首屏加载 p95 不超过 1 秒（100 个账户） |
| 后台 | 不启动定时服务、周期任务或常驻唤醒锁生成验证码 |
| 导出 | I/O 与 KDF 不阻塞主线程，有忙碌状态、防重复提交和可控取消点 |

基准测试需固定一台 Android 10、4 GB RAM、60 Hz 中端实体机并记录型号、系统和构建版本；采用 Release 构建，至少 30 次有效采样。扫码延迟、系统认证及第三方文件提供方延迟单独记录，不混入纯算法指标。

### 6.3 平台与隐私

首版沿用当前工程 minSdk 24。发布前在 API 24、29、31、33 和当前 targetSdk 对应系统验证关键流程。用户卸载应用后本地密钥不应可恢复；产品必须提前说明数据丢失风险以及原服务恢复码的重要性。

## 7. 验收清单

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 标准二维码及缺省参数 | 正确进入确认页，仅确认后保存，重启后记录存在 |
| AC-02 | 非法二维码、重复参数、冲突 issuer、超长输入 | 明确失败，无崩溃、无落库、无跳转执行 |
| AC-03 | 手动输入与校验 | Base32 规范化正确；缺失字段、位数、周期和密钥长度约束生效 |
| AC-04 | RFC 向量 | RFC 6238 三种算法全部时间向量通过，RFC 4226 截断与前导零通过 |
| AC-05 | 时间边界 | 0 秒边界、后台恢复、手动改时间及改时区后输出符合预期 |
| AC-06 | 重复与删除 | 重复凭据必须确认；删除有确认，不影响其他账户 |
| AC-07 | 加密导出 | 独立测试解密后与导出快照一致；两次导出盐及 nonce 不同 |
| AC-08 | 导出篡改 | 错误口令、修改密文/盐/nonce/AAD、截断文件均无法成功认证 |
| AC-09 | 明文导出 | 每行 URI 可被独立解析，编码与参数完整；导出前认证和风险确认不可绕过 |
| AC-10 | 存储与系统备份 | 数据库、备份、日志及持久化 UI 状态中不存在可直接读取的敏感明文 |
| AC-11 | 故障 | 磁盘写入失败、取消文件选择、相机拒绝、密钥失效均有可恢复反馈，不假报成功 |
| AC-12 | 生命周期与锁屏 | 冷启动、后台返回、进程重建和导出返回不泄露锁定内容 |
| AC-13 | 国际化与可访问性 | 中文、英文、TalkBack、200% 字体与窄屏检查通过，无硬编码 UI 文本 |
| AC-14 | 性能 | 达到第 6.2 节约定，记录测试设备及结果 |
| AC-15 | 架构 | 实现不跨模块依赖 impl/UI，不使用事件总线，详见开发规范 |
